## Why
NFR-PRIV-5 needs a server-side delete of the caller's `auth.users` row. D-0135 makes it a fourth Edge Function. The contract comes first, so the backend (T-0310b) and the web (T-0310c/d) code against the same `DELETE /account`.

## Scope
- In:
  - `api/openapi.yaml`, exactly as D-0135 §1 says:
    - the new `account` tag;
    - the `/account` → `delete` operation (`operationId: deleteAccount`, `tags: [account]`, the summary text verbatim, a description, responses `"204"` with no `content`, `"401"` → `Unauthorized`, `"500"` → `Internal`);
    - `info.description` saying "four" functions.
  - Regenerate `packages/shared/src/api.gen.ts` with `pnpm --filter @workoutlab/shared gen:api`. `session-plan.validate.gen.ts` must come out byte-identical, because no schema changes.
  - `packages/shared/test/openapi.test.ts`:
    - AC2 lists the four operations;
    - the AC5 expected-responses map adds `"DELETE /account": ["401", "500"]`.

    These are the only edits to existing tests.
  - A new test file `packages/shared/test/t0310a-delete-account.test.ts` for the ACs below.
  - Edge cases: a repeat delete (the description says 401, never 404), no request body, no new error code.
- Out:
  - The function itself (T-0310b), `supabase/**`, the vendor copy (regenerated by the orchestrator at merge, D-0053 §1), any web code, `docs/data-model.md` (unchanged) and every component schema.
