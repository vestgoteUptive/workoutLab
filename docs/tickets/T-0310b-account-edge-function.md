## Why
NFR-PRIV-5: after confirmation, the auth user and every owned row are deleted immediately. The cascade exists (D-0020, pgTAP `007_account_deletion.test.sql`). The missing piece is a privileged call that only the verified caller can trigger, for themselves only. D-0135 puts it in a fourth Edge Function. The service-role key is fenced in one file, and the existing AC12 guard becomes an allow-list of that file, so the key can't spread.

## Scope
- In:
  - `supabase/functions/account/`:
    - `admin.ts`: the only reader of `SUPABASE_SERVICE_ROLE_KEY`. It exports `deleteAuthUser(userId: string): Promise<void>`, which builds the admin client with `persistSession: false, autoRefreshToken: false` and makes exactly one `auth.admin.deleteUser(userId, false)` call. It throws on an admin error or a missing env var. It has no `.from(`, `.rpc(`, `.storage` or `.schema(`.
    - `core.ts`: exports `createAccountHandler(deps: {authenticate, deleteAuthUser})`, which returns `createHandler("account", {"DELETE /account": …})`. The handler calls `deps.authenticate(req)`, then `deps.deleteAuthUser(ctx.userId)`, then returns `new Response(null, {status: 204})`. A throw from `deleteAuthUser` becomes 500 `internal` (`createHandler` already maps any non-ApiError throw).
    - `index.ts`: `Deno.serve(createAccountHandler({authenticate, deleteAuthUser}))`.
  - `supabase/functions/_shared/cors.ts`: `Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS` (D-0135 §4).
  - `supabase/config.toml`: `[functions.account]` with `verify_jwt = false`.
  - `supabase/tests/scripts/functions-platform.test.mjs`: the AC12 service-role test becomes the D-0135 §3 allow-list. This is the only edit to an existing test besides the AC5 CORS line (below).
  - New tests:
    - `supabase/tests/functions/unit/account.test.ts` (Deno, no stack);
    - `supabase/tests/functions/integration/account-delete.test.ts` (real stack).
  - Edge cases:
    - zero history (a user with no profile at all);
    - a user with 2 years of data;
    - a repeat call;
    - another user's data is untouched;
    - a token for a user who is already gone;
    - a missing key;
    - an admin error.
- Out:
  - Any migration or SQL function (D-0135 §5).
  - `api/openapi.yaml` (T-0310a).
  - Any web code (T-0310c/d).
  - The functions `workouts`, `balance` and `sessions`, apart from the shared CORS method list.
  - The vendor copy (regenerated by the orchestrator after T-0310a).

## Acceptance criteria
Each new test title starts with `T-0310b ACn`. AC1–AC7 are Deno unit tests with injected fakes. They are red on `main` because `supabase/functions/account/` doesn't exist and the CORS list lacks DELETE. Record the red run in the build log. AC8–AC10 run on the real local stack.

- **AC1 (success)**
  - **Given** `createAccountHandler` with a fake `authenticate` resolving `{userId: "U1", supabase: <unused>}` and a recording fake `deleteAuthUser`, **When** `DELETE http://localhost/functions/v1/account` arrives with `Origin: http://localhost:5173`, **Then**:
    - the status is 204 and the body is empty (`await res.text()` is `""`);
    - `x-request-id` matches `^req_[0-9a-f-]{36}$`;
    - `Access-Control-Allow-Origin` is `http://localhost:5173`;
    - `deleteAuthUser` was called exactly once, with `"U1"`.
  - The same request with the bare path `/account` gives the same result.
- **AC2 (the user id only comes from the verified token)** A request with body `{"userId": "U2"}`, query `?userId=U2` and header `x-user-id: U2`, and `authenticate` resolving `U1`, still calls `deleteAuthUser("U1")` exactly once. `U2` never appears in any call.
- **AC3 (401)**
  - When `authenticate` throws `unauthorized()`, the status is 401, the body validates as `ApiError` with `code: "unauthorized"`, and `deleteAuthUser` is **never** called.
  - With the real `authenticate`, each of these gives 401 and no `deleteAuthUser` call:
    - no `Authorization` header;
    - `Authorization: Basic x`;
    - a JWT whose `exp` is 1 h in the past.
- **AC4 (500)**
  - When `deleteAuthUser` rejects with `new Error("admin down: a@b.se")`, the status is 500 and the body is exactly `{error: {code: "internal", message: "Something went wrong", requestId}}`. The raw body contains neither `a@b.se` nor `admin down`.
  - Separately, `admin.ts`'s `deleteAuthUser` with `SUPABASE_SERVICE_ROLE_KEY` unset (stub `Deno.env`) rejects without making a network call.
- **AC5 (routing and CORS)**
  - `GET /account`, `POST /account`, `PUT /account` and `DELETE /account/extra` are each 404 with `code: "not_found"`, and `deleteAuthUser` isn't called.
  - `OPTIONS /account` from `http://localhost:5173` gives 204, and its `Access-Control-Allow-Methods` contains `DELETE`. Update the T-0203b AC15 test's expectations only by adding this assertion.
  - **Contrast:** a disallowed origin gets no `Access-Control-Allow-Origin`.
- **AC6 (the key fence, D-0135 §3)** The edited `functions-platform.test.mjs` asserts that:
  - the set of files under `supabase/functions/` (vendor excluded) matching `/Deno\.env\.get\(\s*["']SUPABASE_SERVICE_ROLE_KEY["']/` is **exactly** `["account/admin.ts"]`;
  - `account/admin.ts` has exactly one match of `auth.admin.deleteUser(`;
  - `account/admin.ts` has zero matches of `.from(`, `.rpc(`, `.storage` and `.schema(`;
  - `account/core.ts` and `account/index.ts` don't contain `SERVICE_ROLE`;
  - `_shared/auth.ts` still doesn't read the key.

  **Contrast (non-vacuity):** the test fails if `admin.ts` stops reading the key, because the set would be empty and the test requires it to be exactly one file. Show this once in the build log with a temporary local edit, then revert it.
- **AC7 (log line, NFR-PRIV-7)** One AC1 request and one AC4 request each produce exactly one `console.log` line. Its keys are exactly `fn`, `ms`, `requestId`, `status`, with `fn: "account"`. The line contains neither `U1` nor `a@b.se`.
- **AC8 (real stack: cascade through the function)**
  - **Given** users A and B, created with `createTestUser()`. A owns:
    - a profile and 9 `area_targets`;
    - 2 sessions with 6 `session_sets`, one of them tombstoned;
    - 1 routine with 2 `routine_items`;
    - 1 `plan_checkins` row.

    B owns one row of each kind.
  - **When** `callFunction("/account", {method: "DELETE", accessToken: A})` runs, **Then**:
    - the status is 204;
    - `admin.auth.admin.getUserById(A)` returns an error or a null user;
    - read through the admin client, A has 0 rows in each of `profiles`, `area_targets`, `sessions`, `session_sets`, `routines`, `routine_items` and `plan_checkins`;
    - B's counts are unchanged (1 each, 9 targets if seeded with `seedFullProfile`);
    - `callFunction("/balance?tz=Europe/Stockholm", {accessToken: B})` is 200.
- **AC9 (real stack: repeat call and a user with no profile)**
  - Repeating AC8's call with A's old token gives 401 (`code: "unauthorized"`), never 404 or 500.
  - A fresh user C with **no** profile and no rows (zero history): DELETE gives 204, and C is gone.
- **AC10 (real stack: 2 years of data within 10 s, NFR-PRIV-5 "immediately")**
  - **Given** user D with a profile, 9 targets, 400 sessions spread over 730 days and 5,000 `session_sets`, inserted in batches of at most 500 through D's own client.
  - **When** DELETE runs, **Then** the status is 204 within 10,000 ms of wall time (measured around the call only, not the seeding), and D has 0 `session_sets` afterwards.
  - The test has a 120 s timeout for the seeding.
- **AC11 (config)**
  - `supabase/config.toml` has `[functions.account]` with `verify_jwt = false`. `supabase/tests/scripts/config.test.mjs`, or the new unit file, asserts it.
  - The three existing `[functions.*]` entries are unchanged.
