## Why
D-0268 lifts the D-0262 parking: the engine will price a one-side set at two sides of work (T-0978b). For that, the flag has to travel on the `LibraryExercise` that the engine receives. Today it does not: `api/openapi.yaml` `LibraryExercise` has `additionalProperties: false` and no `unilateral`; `packages/shared/src/mappers.ts` `toLibraryExercise` does not copy it (D-0263 §1 kept it on the web-only `ExerciseDetail`); and three guards assert the opposite on purpose. Both the web cache (`refreshLibrary` in `apps/web/src/lib/offline/history.ts`) and the Edge Functions (`supabase/functions/_shared/repo.ts`, through the vendored shared copy) build their library with `toLibraryExercise`, so one mapper change reaches the client and the server.

## Scope
- In:
  - **`api/openapi.yaml`** `LibraryExercise`: an optional property `unilateral` (`anyOf` the enum `arm`, `leg`, `side`, and `null`), not added to `required`; the description names D-0268. A second `examples` entry shows a flagged row (for example `dumbbell-row` with `unilateral: arm`). Additive, like D-0264.
  - **`packages/shared/src/api.gen.ts`** regenerated with `pnpm --filter @workoutlab/shared gen:api` (never hand-edited).
  - **`packages/shared/src/mappers.ts`** `toLibraryExercise`: copies the flag **only for a flagged row** (`toUnilateral(row)` non-null), so an unflagged row's object has no `unilateral` key and is identical to today's.
  - **`docs/data-model.md`**, the `exercises.unilateral` note: from "Web-only: the engine never reads it (D-0262)" to "Carried on `LibraryExercise`; read by the engine's time model only (D-0268)". No column, no migration.
  - **Vendored shared copy** `supabase/functions/_shared/vendor/shared/**` regenerated by `node supabase/scripts/vendor.mjs`. The vendored **engine** copy is not touched here.
  - **Guards flipped** (the intended change, not a weakened test):
    - `packages/shared/test/unilateral-boundary.test.ts`: from "engine and its vendored copy have no `unilateral`" to an allow-list: only `packages/engine/src/types.ts` and `packages/engine/src/cost.ts` (and their vendored counterparts `supabase/functions/_shared/vendor/engine/types.d.ts`, `cost.js`, `cost.d.ts`) may mention it. It passes today (no mentions) and keeps passing when T-0978b lands.
    - `packages/shared/test/mappers.test.ts` (the assertion at about L283 that the mapped key list does not contain `unilateral`): flagged row now has it, unflagged does not.
  - **Web cache test (listed extra):** `apps/web/src/lib/offline/__tests__/unilateral-cache.test.ts` gains the cases in AC5. No production web file changes: `refreshLibrary` already maps through `toLibraryExercise`, and `effectiveLibrary` spreads the row.
- Out:
  - Any engine change (T-0978b), any migration, `database.gen.ts`, `data/exercises/**`, any other openapi schema.
  - An IndexedDB version bump (D-0263 §2, D-0268 §6): rows cached before this ticket have no key and read as both sides until the next `refreshLibrary`.

## Acceptance criteria
Test titles start `T-0978a ACn`.
- **AC1 (the schema).** Given `api/openapi.yaml`, When `schemas.test.ts` validates `LibraryExercise`, Then `unilateral` is an optional property (`required` is unchanged), `additionalProperties` is still `false`, both examples validate, and a value `"both"` or `""` or `1` is rejected. The generated type `LibraryExercise["unilateral"]` is `"arm" | "leg" | "side" | null | undefined` (`types.test.ts`, `expectTypeOf`).
- **AC2 (the mapper, flagged and unflagged).**
  - Given an `exercises` row with `unilateral: "arm"` (and the same for `"leg"`, `"side"`), When `toLibraryExercise(row, areas)` runs, Then the result has `unilateral` with that value and every other field exactly as before.
  - Given `unilateral: null`, a missing field (a row read before T-0972), `"both"` or `""`, Then the result has **no** `unilateral` key (`Object.keys` and `toStrictEqual` against the old output shape for `backSquatRow`).
- **AC3 (no migration, no column change).** Given the repo after this ticket, Then `git status` shows no new file under `supabase/migrations/` and no change to `packages/shared/src/database.gen.ts` (stated in the log; the T-0972 pgTAP file is untouched).
- **AC4 (vendor).** Given the regenerated vendor copy, Then `node supabase/scripts/vendor.mjs --check` exits 0, the vendored `mappers.js` contains the flag mapping, and `supabase/functions/_shared/vendor/engine/**` is byte-identical to before.
- **AC5 (the web cache carries it, online and from an old cache).**
  - Given `refreshLibrary()` over rows where `dumbbell-row` has `unilateral: "arm"` and `back-squat` has none, When it finishes, Then the `libraryCache` row for `dumbbell-row` has `exercise.unilateral === "arm"`, the row for `back-squat` has no `unilateral` key, and `exerciseDetails` still carries `unilateral` as T-0972 left it.
  - Given a `libraryCache` row written before this ticket (no key), When `loadLibrary()` reads it, Then `unilateral` is `undefined` and nothing throws (the old-cache sibling, D-0197 §7).
  - Given a flagged row and a weight-step override for it, When `effectiveLibrary` runs, Then the returned row keeps `unilateral` and has the overridden `incrementKg`.
- **AC6 (the guards).**
  - `unilateral-boundary.test.ts` exposes a pure scanner `scan(files)`. Given inline fixtures: a mention in `packages/engine/src/cost.ts` Then 0 findings; in `packages/engine/src/types.ts` Then 0; in `packages/engine/src/session.ts` or `balance.ts` or `prefill.ts` Then 1 finding naming the file; in `supabase/functions/_shared/vendor/engine/session.js` Then 1.
  - On the real tree it reports 0 findings and asserts it read more than 5 engine files (not vacuous).
  - Planted fault: add a comment mentioning `unilateral` to a backup copy of `packages/engine/src/balance.ts`: the guard goes red naming it; restored with `cp`, green.
- **AC7 (the doc).** Given `docs/data-model.md`, When a source-scan test in `packages/shared/test` reads the `unilateral` row, Then it names D-0268 and no longer contains "the engine never reads it" (found the row: not vacuous).

Binary-condition check (D-0197 §7): flagged and unflagged row (AC2, AC5); cache written before and after this change (AC5); engine file allowed and not allowed (AC6). A tombstoned or rejected row state does not apply: `exercises` has none (stated in T-0972); the mapper fixtures include rows with null and non-null values.
