## Context
The four tickets were checked against `main` after T-0304d, T-0421 and T-0431 merged. That check found these open points:

1. **Entering an item at a logged set (T-0414 review, T-0415).** `enterItem` in `features/UF-09/machine.ts` always enters set index 0 (READY, COUNTDOWN_END, SKIP_WARMUP). While the List view is open the machine keeps running (`keepsClockRunning: true`). So a List-view log of item N set 1 during UF-09.6 leaves READY on a position that is already logged.
2. **A swap from a pause taken on UF-09.4 (D-0140 Consequences, T-0422).** D-0140 left `confirm` at "clamp only". Once T-0422 mounts Swap on UF-09.9, the user can pause on UF-09.4, swap the current item and resume. UF-09.4 then shows the new exercise's name (`confirm-set.tsx` reads `ctx.plan.items[itemIndex]`) over the old exercise's recorded values. An edit and Save then re-stamp the focus-state entry with the new `exerciseId` (`stamp`), while the queued set keeps the old one, because `editSet` sends no `exerciseId`.
3. **REST_END after the last item (T-0415, D-0142 Context 3).** D-0149 §4 already makes `CHECK_RESOLVED` past the end go to `done`, so the store no longer reaches an out-of-range `next`. The reducer still returns `betweenItems`, so the store still calls the check point resolver for an item that doesn't exist.
4. **UF-03.3's rating source (T-0420 review, T-0433).** `loadSummary` preselects from the raw queued row, and an untouched Save sends that rating again. Under D-0148/D-0151 the merged `loadSessions()` view can hold a newer rating from another device. A marked flushed entry, for example, defers to the cache. Re-sending the raw value overwrites that newer rating.
5. **Save after leaving (T-0433).** `EffortSave` calls `navigate("/", {replace: true})` when the write resolves, even if the user has already left through "See balance" or Back.
6. **A failed finish after a landed plan write (T-0304d re-review, T-0435).** `finish()` waits for a pending UF-09.8 plan write. If that write lands while `finish()` is waiting, `createPlanApply` sees `writes.finishing` and doesn't call `applyPlan`. If the ended-row write then rejects, the row holds the new plan but the store walks the old one, so Continue walks items the user just trimmed away.

## Decision
1. **Entering an item starts at its first free set (T-0415).** `enterItem` enters `firstUnloggedSet(state, ctx, itemIndex)`, which is set index 0 when nothing is logged. In focus mode without the List view nothing changes. If the item has no free position, it counts as complete. On the last item that is `done` (timer null). On any other item it is `betweenItems`, and the store's check point then runs for the item after it. A timed item's 3 s position timer starts for the set it enters.
2. **A swap of the current item while UF-09.4 is in play saves the recorded set as recorded (T-0422; amends D-0140 §1).** When `PLAN_REPLACED` targets the current item and `phase` is `confirm`, or `paused` with `resumePhase: "confirm"`:
   - The recorded entry stays exactly as it is in `loggedSets`, old `exerciseId` included. No edit is applied, so the result is what the 5 s auto-save would have produced.
   - The machine goes where `SAVED` with no edit goes (`afterSet`), using the **new** item's set count and `restFor` of the new exercise. `setIndex` is first clamped into the new item (`min(setIndex, setsInItem(newItem) − 1)`), so the stored state stays in range (D-0111 §7).
   - Not paused: a `rest` that starts at `atMs`, or `done` after the last set of the last item.
   - Paused: `resumePhase: "rest"` with the rest starting at `pausedAtMs`, so RESUME leaves the full rest. A result of `done` ends the pause, as D-0140 §4 does.
   - Every result passes `isValidFocusState`. A `PLAN_REPLACED` for another item still returns the same state. The T-0414 AC5 clamp-only pin drops its `confirm` row as a named change; its `rest`, `next` and paused-on-rest rows stay.
3. **REST_END on the last item with no free set is `done` (T-0415, D-0142 §2).** This is now a reducer rule and not only a store effect (D-0149 §4). The store calls no check point for it.
4. **UF-03.3's rating comes from the merged view (T-0433; amends D-0142 §4).**
   - **Preselect.** At load, the chip is `storedEffort(view.effortRating)`, where `view` is the `loadSessions()` entry with this `id`. With no such entry, it is the raw row's `effort_rating`, as today.
   - **Untouched Save.** If the user picked no chip during this mount, Save sends `storedEffort(view.effortRating)` from a `loadSessions()` read at the tap (D-0071 §6), or the raw row's value when there is no entry.
   - **A pick.** Save sends the picked value, as today.
   - **The rest of the row.** Save still sends `{...row, effort_rating}` from `offlineDb().sessions.get(id)` read at the tap, so `ended_at` and `plan` are the stored ones. `now` stays the raw row's `ended_at`.
5. **Save navigates only while the summary is still mounted (T-0433).** If the summary has unmounted by the time the write resolves (the user followed "See balance", or Back), there is no `navigate`. The write still lands. A rejection after unmount shows nothing and logs no React warning.
6. **A failed finish applies the plan write it waited for (T-0435).** If `finish()` rejects after a plan write it waited for had landed (the row now holds the new plan), the store applies that plan exactly as the write would have without the finish: `applyPlan` → `PLAN_APPLIED` (D-0149 §1 while paused), and `row` becomes the written row. This happens before `finish()`'s promise rejects. A plan write that rejected applies nothing. A finish that succeeds applies nothing, so the ended row stays the last write and the store doesn't move after it. A later Trim, Skip next or End works as it does with no failed finish.

## Consequences
- T-0415 implements §1 and §3. T-0422 implements §2, with a listed extra for `machine.ts` and `machine.session.test.ts`. T-0433 implements §4 and §5. T-0435 implements §6.
- No contract change. Every rule is device-local focus state or a read of IndexedDB.

## Revisit when
- Users want to edit the recorded set after swapping from UF-09.4. Then the swap would wait for Save, not save it.
- The summary gets a refresh. Then the untouched Save could compare the mount-time and tap-time values.
- `finish()` gets a retry UI of its own.
