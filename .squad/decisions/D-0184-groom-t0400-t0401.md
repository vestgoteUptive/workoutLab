## Context
The human started phase 4. T-0400 and T-0401 are the first tickets that act on real accounts:
- the hand-made prod Supabase project `csgjsdwuxqtuqpuazzpz` (D-0011);
- the shared Cloudflare zone `vestgote.com`, which carries records that aren't the squad's.

A wrong `apply` here can't be undone with `git revert`. A mismatched import makes Terraform
"fix" live prod auth settings, and a stray zone-level resource changes the whole zone. H-02 and
H-03 are done, so the tokens are in `.env.local`.

The devops role already says "apply only when the orchestrator's input says `apply: true`". It
doesn't say what the human sees first, or what may be applied.

## Decision
1. **Plan-then-stop is a hard gate for every Terraform ticket.**
   - **Run A:**
     - read-only discovery;
     - config;
     - `terraform plan -out=infra/terraform/plans/<root>.tfplan`;
     - the full `terraform show` text pasted into the ticket's build log;
     - commit, then hand back `blocked` with "plan ready for human review".
   - The orchestrator raises the review as an H-item.
   - **Run B** runs only with `apply: true`, and applies only **the saved, reviewed plan
     file**. If it is stale, Terraform refuses it, and the builder goes back to run A.
   - Planning and applying in one run fails the ticket.
   - In run A there is no `terraform import`, no `state` command, and no write call to the
     provider API.
2. **Discover, then import what exists.**
   - Before writing a resource, the builder reads the live object with GET calls only.
   - Anything that already exists is imported through `import {}` blocks, so the import is part
     of the reviewed plan. Only what is missing gets created.
   - When reality differs from a decision, the config mirrors reality, so the import changes
     nothing. The difference goes in the log for the human. It is never "corrected" inside the
     import ticket.
3. **Blast radius.**
   - There is one root module per surface, each with its own local state: `supabase-prod` and
     `cloudflare` (no `supabase-staging`, §5 below). A Cloudflare/DNS run can't touch prod
     Supabase.
   - The prod project has `prevent_destroy`.
   - Plan-scope scripts (`.github/scripts/check-infra-plan-supabase.mjs`,
     `check-infra-scope-cloudflare.mjs`) fail on any address outside the ticket's allowlist,
     any `delete`, and any change to an imported resource.
   - On the zone, the builder takes a count and a SHA-256 baseline of every record except the
     two hostnames, before and after the apply. The names of other people's records are never
     written down.
4. **Secrets.**
   - Provider tokens and IDs come from `.env.local` through the environment. There are no
     `.tfvars`.
   - State, plans, `.tfvars` and `.terraform/` are gitignored (T-0400 AC-1); the lock file is
     committed.
   - The Google OAuth client secret stays out of Terraform altogether. It is set by hand (H-08),
     never named in the config, and a check proves it is absent from the plan.
   - Raw Management API auth responses (which hold secrets) are never printed, only filtered
     fields.
5. **No staging environment (human decision, 2026-10-05, supersedes this decision's original
   §5/§6 below as drafted).** Two environments only: **local** (Docker `supabase start`, for
   dev) and **prod** (the one real cloud project). There is no second Supabase org, no
   `workoutlab-staging` project, and no T-0400b ticket. `docs/infra-costs.md`'s staging-org
   line and D-0006's "environments: local/staging/prod" line are now stale and need a follow-up
   edit (T-0404 or a dedicated docs ticket, not blocking T-0400/T-0401).
   - **Branch previews point at prod, not a second project** (human decision). This is a real
     risk surface a staging environment would have avoided: a preview build's own test/dev
     activity can read and write real prod data. T-0402 (not this ticket) must address it
     directly — e.g. RLS policies that already scope every table to `auth.uid()` reduce the
     blast radius to "a signed-in preview tester can only touch their own rows," but T-0402's
     own spec should state this explicitly and verify it holds, rather than assume it. Flag this
     as a named risk in T-0402's own Why section when that ticket is groomed.
6. **Redirect allow-lists (amends D-0010's single list).**
   - **T-0400 stays zero-change.** It imports prod with D-0011's exact three entries
     (`http://localhost:3000/**`, `http://localhost:5173/**`,
     `https://app.workout.vestgote.com/**`) and nothing else — the preview pattern is a real,
     deliberate change to prod, not a reflection of what's already there, so it does NOT belong
     in the import ticket. Mixing a real change into the one ticket whose entire design and
     AC-5 prove "this plan changes nothing" would defeat that gate's purpose.
   - **The preview pattern** `https://*.workoutlab-web.pages.dev/**` is added to prod's
     allow-list as its own step inside **T-0402** (deploy pipelines), once previews actually
     need it — a small, explicitly-reviewed `terraform plan` showing exactly that one addition,
     following the same plan-then-stop gate as T-0400/T-0401. T-0402's own Why section must
     name the risk this creates (a preview build's signed-in tester can read/write real prod
     data, scoped only by RLS to their own rows) and its AC must prove RLS actually holds for
     every table a preview touches before the allow-list change ships.
   - **The landing host** has no auth flow. It is added to prod, if at all, together with the
     `site_url` switch at H-06 (T-0402).
   - Google sign-in on prod is unaffected (D-0011); previews use whatever auth a signed-in
     tester already has on prod.
7. **Cloudflare.**
   - Pages projects are direct-upload: no git source, no GitHub app. They are named
     `workoutlab-web` (the name T-0309 already uses) and `workoutlab-landing`, unless discovery
     finds hand-made ones, which are then imported under their own names.
   - Each hostname gets a `cloudflare_pages_domain` plus a proxied CNAME to `<project>.pages.dev`
     (D-0010).
   - "HTTPS works" means an `active` domain status and a TLS handshake that verifies. The HTTP
     status isn't asserted, since nothing is deployed before T-0402 (gate 3).
8. **Parallel.** T-0400 and T-0401 may build at once. Their only shared file is `.gitignore`,
   and both append an identical block.

## Consequences
- The board gets T-0400 and T-0401 → `ready`. No T-0400b, no new H-item: the human decided
  (2026-10-05) there is no staging environment, only local (dev) and prod.
- `docs/infra-costs.md`'s staging-org line and D-0006's "local/staging/prod" environment list
  are now stale and need a follow-up docs ticket (not blocking T-0400/T-0401).
- T-0402 (deploy pipelines, not yet groomed) inherits two new obligations from this decision:
  add the preview redirect pattern to prod's allow-list as its own small, reviewed plan step
  (never folded into T-0400's zero-change import), and prove RLS scopes a preview tester's
  reads/writes to their own rows before that allow-list change ships — previews now touch real
  prod data, which a staging environment would have avoided.
- The orchestrator files a plan-review H-item each time a run A (T-0400 or T-0401) hands back
  `blocked` with "plan ready for human review."
- A follow-up for the devops role (`agents/roles/devops.md`) points it at this gate's exact
  wording.
- **Revisit when:** remote state lands (R2), CI starts running `terraform plan`, or the no-
  staging decision is reconsidered (e.g. if RLS can't be proven safe enough for prod previews
  in T-0402, reinstating a staging environment is the fallback).
