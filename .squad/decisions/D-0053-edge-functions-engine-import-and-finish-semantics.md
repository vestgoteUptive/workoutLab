## Context
T-0203 builds the three D-0037 paths as Supabase Edge Functions (Deno). They must run the same
`@workoutlab/engine` code as the device (principle: deterministic engine, D-0024) and the
`@workoutlab/shared` row mappers (T-0102b). Neither package is published: both expose raw
`src/*.ts` with `.js` import specifiers (TS NodeNext style), and `@workoutlab/shared` imports
`ajv/dist/2020.js`. Deno resolves neither the pnpm workspace nor `.js` → `.ts` without sloppy
imports, and `supabase functions deploy` bundles most reliably when every imported file lives under
`supabase/functions/`. Docker on the orchestrator host can't pull images, so any strategy has to be
checkable without the local stack.

D-0037 §9 (and the `finishSession` description) say both "a later `endedAt` overwrites it" and
"last write wins". These disagree when an offline queue replays two finishes out of order.
D-0037 also leaves open which clock and which targets the finish summary uses, and whether the
gateway or the function returns the 401.

## Decision
1. **Engine and mapper import: a committed tsc build behind an import map.**
   - `supabase/scripts/vendor.mjs` compiles `packages/engine/src/**/*.ts` and
     `packages/shared/src/**/*.ts` (not tests) with the workspace TypeScript and
     `supabase/scripts/tsconfig.vendor.json` (ES2022 modules, `declaration: true`, no bundling) into
     `supabase/functions/_shared/vendor/engine/` and `supabase/functions/_shared/vendor/shared/`.
     The output is plain ESM `.js` plus `.d.ts`. Its `.js` specifiers resolve natively in Deno.
     The output is committed, and each file starts with a `// GENERATED by supabase/scripts/vendor.mjs — do not edit` header.
   - `supabase/functions/deno.json` maps `@workoutlab/engine` → `./_shared/vendor/engine/index.js`,
     `@workoutlab/shared` → `./_shared/vendor/shared/index.js`, `ajv/dist/2020.js` →
     `npm:ajv@<the exact version in pnpm-lock.yaml>/dist/2020.js`, and `@supabase/supabase-js` to a
     pinned `npm:` version.
   - Function code imports only the bare names `@workoutlab/engine` and `@workoutlab/shared`. It
     never imports `_shared/vendor/**` by path or anything under `packages/`.
   - `node supabase/scripts/vendor.mjs --check` rebuilds into a temp dir and exits 1 if anything
     differs from the committed copy. CI runs it, so the server engine can't drift from the
     device engine.
   - Rejected: an import map pointing at `../../packages/*/src` with `unstable: ["sloppy-imports"]`
     (depends on the edge runtime flag and on deploy bundling files outside `supabase/functions`).
     Also rejected: an esbuild bundle (new dependency, and a single opaque file).
2. **The seed is generated too.** `node supabase/scripts/gen-seed.mjs` reads
   `data/exercises/library/*.json` in id order and writes `supabase/seed.sql`, which is committed
   and byte-for-byte deterministic. It writes **every** `exercises` column explicitly and never
   relies on a column default: `external_load = NOT bodyweight` (D-0044 §1, §3), `increment_kg` =
   JSON value or `2.5` (D-0044 §4), and absent optional fields become `NULL` or `'{}'`. It also
   writes `exercise_areas` from `areas` and `exercise_variants` from `variants`, as upserts
   (`on conflict … do update`) so running the seed twice is a no-op. `--check` exits 1 on drift.
   The script uses only Node built-ins (no new dependency, no TS runner).
3. **Function layout matches the OpenAPI server URL `/functions/v1`.** There are three functions:
   `workouts` (serves `POST /workouts/suggest`), `balance` (serves `GET /balance`) and `sessions`
   (serves `POST /sessions/{id}/finish`). Any other method or sub-path on them returns 404
   `not_found` in the ApiError envelope (no 405, which the contract doesn't have). `OPTIONS`
   returns 204 with CORS headers for the origins in `ALLOWED_ORIGINS` (env). The default is D-0011's
   allow-list: `http://localhost:3000`, `http://localhost:5173`, `https://app.workout.vestgote.com`.
4. **Auth in the function.** `[functions.<name>] verify_jwt = false` in `config.toml`, so that the
   gateway never answers with a non-ApiError 401. Each function verifies the bearer token with
   `supabase.auth.getUser(token)` and returns 401 `unauthorized` in the envelope when it's missing,
   malformed or expired. All data reads and writes use a client that carries the caller's JWT, so
   RLS applies. No function uses the service-role key for user data. A session the caller doesn't
   own is therefore invisible, which gives 404 (D-0037 §4).
5. **requestId.** Every response from these functions, success or error, has
   `requestId = "req_" + crypto.randomUUID()`. It appears in the ApiError body, and in an
   `x-request-id` response header on every response (the header is not a contract field). Each
   request logs one JSON line `{requestId, fn, status, ms}`, with no user id, email or token
   (NFR-PRIV-7). A 500 body is always `{code: "internal", message: "Something went wrong"}` and
   never includes a stack trace.
6. **Clock and history window.** `now` is the server clock, read once per request at the handler
   boundary and passed to the engine as an ISO string. The engine never reads a clock. History =
   the caller's `session_sets` (tombstones included, rule 0 drops them) with `completed_at ≥ now −
   56 days` (D-0034 §3), mapped with `toHistorySet`. Library = every `exercises` row (both kinds)
   with its `exercise_areas`, mapped with `toLibraryExercise`.
7. **Finish keeps the latest `endedAt` (resolves D-0037 §9).** Let `stored` be `sessions.ended_at`.
   - `stored` is null, or request `endedAt` > `stored`: write `ended_at = endedAt`, and write
     `effort_rating` when the request carries it.
   - Request `endedAt` = `stored`: write only `effort_rating`, if it's present. This is a retry
     that adds the rating.
   - Request `endedAt` < `stored`: write nothing.
   - In every case, return 200 with the summary for the row as stored after the call.
   The rule is a max, so it's commutative: any replay order of the same set of finishes ends in the
   same row. "Last write wins" in D-0037 §9 means "the latest `endedAt` wins", not "the last request to arrive".
   > **AMENDED by D-0058 (2026-09-28).** The three bullets above do **not** actually deliver the
   > row-level commutativity this paragraph claims: a rating written by a non-older request survives,
   > while an older request's rating is discarded, so `effort_rating` depends on arrival order.
   > D-0058 fixes bullet 1 — a strict win writes `effort_rating = request.effortRating ?? NULL`,
   > so the winning finish decides the whole row. Implement D-0058, not these bullets.
   `endedAt < started_at` → 400 `invalid_request`, checked before the DB check can raise a 500.
   There's no upper bound against the server clock: a skewed device clock is stored as sent.
8. **Finish summary is a pure function of the stored row.** `balance` in the summary is
   `balance(history, targets, library, now = stored ended_at, tz)`, not the server clock, so a
   repeat finish returns a deep-equal summary. `durationS = floor((ended_at − started_at) / 1000)`.
   `withinBudget = durationS ≤ time_budget_min × 60 + 120`, boundary included (D-0037 §9).
   `hardSets` = the session's live (not tombstoned), non-warm-up sets that pass engine
   `isHardSet`. `exerciseCount` = the number of distinct `exercise_id`s among those sets.
   `weightedSetsByArea[a]` = Σ over those sets of the exercise's weight for `a` (1 or 0.5), with
   all 9 keys and 0 when a key has no sets. Finish has no 422 in the contract. When the caller has
   fewer than 9 `area_targets`, the summary uses `deriveTargets(profile)` if a profile exists,
   otherwise `BASE_TARGETS`, each with `source: "default"` and `updatedAt = ended_at`.
9. **Request validation is hand-written in the function** against the three request shapes
   (unknown keys → 400, because every schema is closed). `tz` is valid when
   `new Intl.DateTimeFormat("en", {timeZone: tz})` doesn't throw. The tests validate every
   200 body against `api/openapi.yaml` with Ajv (2020-12) loaded through `npm:` specifiers in the Deno
   tests, so the runtime doesn't parse YAML.

## Consequences
- backend (T-0203): implements 1–9. Scripts live in `supabase/scripts/**` (listed as an extra path
  in the ticket). The `supabase` CI job gains the vendor/seed `--check` steps, `supabase
  functions serve` and `deno test`. That job is listed as an extra path too.
- data (follow-up): reword the `finishSession` description in `api/openapi.yaml` from "last write
  wins" to "the latest `endedAt` wins (D-0053 §7)". This is text only, with no schema change.
- web-shell (T-0300 follow-up): the offline queue must never replay a `sessions` upsert that carries
  `ended_at: null` after a finish. Session upserts go first and finish goes last, because a row-level
  upsert (NFR-SYNC-3) can still clear `ended_at` outside this function.
- engine: no change. Any engine change is picked up by rerunning `vendor.mjs`, and CI fails until
  it's rerun.

## Revisit when
- The Supabase edge runtime resolves pnpm workspace packages (or sloppy imports) in both `serve`
  and `deploy`. Then drop the vendor copy.
- The engine or shared package gains a runtime npm dependency (add it to the import map, or
  reconsider bundling).
- Users need to correct a finish to an earlier time (UF-03.3 has no such control in v1).
- The finish summary should reflect sets synced after `ended_at`.
