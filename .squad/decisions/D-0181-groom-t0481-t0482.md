## Context
T-0471 merged (`b16b2ee`). Two of its follow-ups were candidates:
- **T-0481** already had a ticket. It said to remount `PlanBody` with a `key` bump so the body
  re-reads the cache. But T-0471 moved the one `usePlanData` call up from `PlanBody` into `Plan`
  (`features/UF-11/index.tsx`), so it can gate the card's mount on Plan's phase. `PlanBody` now
  takes `state` as a prop. A key bump on it re-reads nothing.
- **T-0482** was ungroomed. Today (`features/UF-02/Today.tsx`) renders the card through
  `todayCheckinSlot`, a lazy `ComponentType` with no props. `useToday` reads the cache on mount,
  runs one D-0113 refresh, and reads again. Nothing tells it that an Accept changed the cache.
  The card's writes go to Supabase. Only the card's own `refreshAll` call updates the cache.

## Decision
1. **T-0481: the re-read lives in the hook (amends D-0174 §2's mechanism).**
   - `CheckinCard` gets `onAnswered?: () => void`, called once after a successful Accept or Keep,
     after its `refreshAll` settles. This part is unchanged from D-0174 §2.
   - `usePlanData(clock, revision = 0)`: a revision change runs one cache read with no
     `refreshAll`. It never drops back to `loading` or `cold`.
   - `Plan` bumps the revision from `onAnswered`.
   - Neither `PlanBody` nor the card is remounted. A remount would put Plan back in `loading`, and
     a remounted card would re-read a cache that, after a rejected refresh, still holds the
     unanswered proposal, so it would show the card the user just answered. `EditPlanBody` keeps
     the one-argument call.
   - The rest of D-0174 §2's scope stands: called once, never for a failed write, and never for
     the D-0172 §2 hide.
2. **T-0482: a slot prop, with the same revision shape. Not a cache-change signal.**
   - `todayCheckinSlot` is typed `ComponentType<{ onAnswered?: () => void }> | null`, with an
     inline prop type. It adds no UF-11 reference, so T-0471's `slots.tsx` pin (D-0174 §1) holds
     unedited.
   - `useToday` gets an optional `revision` in its cache-read effect's dependencies. The refresh
     effect stays once per mount.
   - `Today` bumps the revision from the slot's `onAnswered`.
   - A `lib/offline` change event was rejected for now, for four reasons:
     - it's another lane (a contract-like surface that every screen could start subscribing to);
     - every `refreshAll` caller would fire it, AutoSync included, and that includes the moments
       while a workout is running (principle 1 risk on any screen that subscribes);
     - only Today needs it;
     - the slot prop reuses the exact shape T-0481 builds.
3. **T-0482 waits for T-0481** (`blocked:T-0481`). The slot's new prop type has to match
   `m.CheckinCard`'s props, or typecheck fails, and T-0482's real-wiring AC needs the prop to
   exist. The two lanes share no files (UF-11 versus UF-02), so once T-0481 is on `main`, T-0482
   runs on its own.
4. **No e2e for either.** `mockSupabaseData` serves static rows, so a post-Accept `refreshAll` in
   Playwright re-reads the old targets. Unit tests against the real `lib/offline` cache (T-0481)
   and mocked loaders (T-0482) carry the proof. Each ticket runs only its own flow's spec
   (D-0178).
5. **Sizes.** T-0481 is about ¼ day and T-0482 about ¼ day. Both are under D-0157 §7's half day.

## Consequences
- T-0481 is `ready`. Its ticket was rewritten against `b16b2ee`.
- T-0482 has a ticket and is `blocked:T-0481` on the board. A later groom flips it to `ready` once
  T-0481 is `done`.
- D-0174 §2's "Today keeps its pre-Accept view until the next mount" ends when T-0482 lands.

## Revisit when
- A second screen besides Today and Plan needs to react to a cache change from another flow. At
  that point, consider the `lib/offline` signal again, owned by the web-shell lane.
- The Supabase e2e mock becomes stateful, so an e2e Accept could prove the re-read end to end.
